# Purchase Cost & Product Profitability — Feature Contract

تاريخ: 2026-11-14. الحالة: **تنفيذ P01–P11 موجود؛ قبول P12 والمراجعة اليدوية معلقة**.

الوثائق المصاحبة: [README](README.md)، [المراحل](PHASES.md)، [التقدم](PROGRESS.md).

## 1. النتيجة المطلوبة

صاحب النشاط يستطيع تسجيل فاتورة شراء بقيمتها، ومعرفة تكلفة المنتج أو الوصفة، ثم مشاهدة الكمية المباعة وصافي مبيعاتها والتكلفة والربح حسب المنتج والمنيو والفرع والفترة.

نستخدم آخر سعر شراء مؤكّد كأساس تكلفة إداري للمبيعات الجديدة. يجب أن تظهر تسمية الأساس في التقارير والتصدير؛ الأرقام ليست ادعاءً بتكلفة دفعات فعلية أو بصافي الربح المحاسبي.

## 2. سجل القرارات

| ID | الحالة | القرار |
| --- | --- | --- |
| D01 | USER-CONFIRMED | آخر سعر شراء مؤكّد يحل محل التكلفة الحالية للمبيعات الجديدة؛ لا متوسط متحرك ولا FIFO. |
| D02 | USER-CONFIRMED | السعر الجديد يشمل المبيعات الجديدة من المخزون القديم أيضًا. |
| D03 | USER-CONFIRMED | المبيعات السابقة تظل بتكلفتها المسجلة؛ لا إعادة حساب بأحدث سعر. |
| D04 | USER-AUTHORIZED | خطة ممتدة بمراحل صغيرة؛ المستخدم قال «go» لبدء التنفيذ المرحلي. |
| D05 | USER-CONFIRMED | التكلفة الحالية لكل merchant + stock item، وسعر واحد للصنف في كل المستودعات. |
| D06 | USER-CONFIRMED | «الأحدث» بحسب ترتيب تأكيد الاستلام في النظام، وليس تاريخ فاتورة المورد أو تعديل المسودة. |
| D07 | USER-CONFIRMED | تكلفة البيع تُثبت عند استهلاك المخزون الفعلي؛ إيراد POS عند تأكيد البيع، وإيراد الطلب الإلكتروني عند قبوله. |
| D08 | USER-CONFIRMED FOR P02 | الخصم يقلل قيمة البنود، والشحن المشترك يتوزع بنسبة قيمة البند قبل التعديلات. الضريبة مؤجلة وغير مدرجة في إجمالي الفاتورة حتى مرحلة منفصلة. |
| D09 | USER-CONFIRMED | يمنع البيع/قبول الطلب عند وجود تكلفة مجهولة لأي خامة أو مكوّن مطلوب. |
| D10 | USER-CONFIRMED | يسجل سداد المورد بربطه بحركة سحب نقدية/خزنة موجودة؛ لا ينشئ السداد حركة نقدية من تلقائه. |
| D11 | USER-CONFIRMED | يمنع تأكيد الفاتورة إذا ظهر للصنف نفسه في حالتي المخزون تكلفة فعالة مختلفة؛ يجب توحيد تكلفة الوحدة الأساسية بعد توزيع الخصم والشحن. |
| D12 | IMPLEMENTATION POLICY | تصحيح السعر مستند جديد لا يعدل الفاتورة الأصلية أو snapshots السابقة؛ يحدث التكلفة الحالية فقط إذا ظلت الفاتورة مصدر التكلفة الأحدث. مرتجع المورد يقلل الكمية ورصيد الفاتورة ولا يفترض ردًا نقديًا. |
| D13 | USER-CONFIRMED | يوزع خصم الكوبون الإلكتروني على الأصناف حسب قيمة كل بند قبل الخصم. تُوزع القروش المتبقية بطريقة أكبر باقي وبترتيب ثابت. |
| D14 | USER-CONFIRMED | تُضاف المبيعات القديمة المؤكدة للتقرير من الإيراد المحفوظ وتظل تكلفتها مجهولة؛ لا تُعدل أسعارها السابقة ولا تُنشأ تكلفة تاريخية. |

قرارات D01–D11 وD13–D14 أكدها المستخدم في هذه المحادثة. D12 سياسة التنفيذ الحالية وليست اختيارًا منفصلًا أكده المستخدم؛ يمكن مراجعتها قبل التوسع في دفتر الأستاذ أو المحاسبة.

## 4. فاتورة الشراء المالية

### الإدخال والعرض

- البند: الصنف، المستودع، حالة المخزون، كمية الشراء، وحدة الشراء، سعر الوحدة، إجمالي البند.
- الفاتورة: المورد ورقمه المرجعي، العملة EGP في البداية، مجاميع البنود، الخصم، المصاريف والضرائب المدعومة، والقيمة النهائية.
- كل مبلغ يوضح هل يخص قطعة أو كيلو أو عبوة؛ حفظ تحويل الوحدة كما كان وقت التأكيد.
- المسودة لا تعدل كمية المخزون أو آخر تكلفة. التأكيد يسجل الكمية وقيمتها ومصدر التكلفة في transaction واحدة.
- الحساب النهائي على الخادم. الواجهة تعرض معاينة ولا تكون مصدر المجاميع الموثوق.
- الفاتورة المؤكدة لا تُعدّل في مكانها؛ التصحيح مستند مرتبط وأثر قابل للتتبع.
- لا نفترض أن المورد استلم المال عند تأكيد البضاعة. قيم الفاتورة والمدفوع والمتبقي مفاهيم مستقلة.

### دقة الحساب

- قيم مالية decimal strings في HTTP. يستخدم P01 حساب BigInt دقيقًا؛ لا حساب مال بـJavaScript floating point.
- المبالغ النهائية EGP بمنزلتين؛ تكلفة الجرام أو المليلتر تحتاج دقة أعلى قبل تقريب إجمالي البند.
- قرار P01: سعر الوحدة بالجنيه حتى منزلتين عشريتين، والكمية تحتفظ بدقتها القائمة حتى 6 منازل. يُحسب إجمالي كل بند بأعداد صحيحة دقيقة ويقرب نصفًا لأعلى إلى القرش؛ إجمالي الفاتورة مجموع إجماليات البنود بعد تقريبها. حد الحفظ هو Decimal(18,2). تُطبّع صيغة السعر إلى منزلتين قبل بصمة idempotency، كي تتساوى `200` و`200.00`.
- قرار P02: الخصم والشحن قيمتان إجماليتان اختياريتان بالجنيه حتى القرش. يوزع كل منهما على إجمالي البند قبل التعديل، بأكبر باقي مع أولوية ترتيب البنود عند التعادل؛ مجموع التوزيع يساوي القيمة المدخلة بالضبط. إجمالي السطر النهائي = إجمالي السطر الأساسي − حصة الخصم + حصة الشحن. الخصم لا يتجاوز المجموع الأساسي، والضريبة غير مدعومة وغير مشمولة بعد.
- تكلفة الوحدة الصفرية غير مدعومة في P01؛ لا تمثل الخانة الفارغة صفرًا، ودعم العينات المجانية يتطلب سببًا صريحًا في مرحلة لاحقة.
- الخصومات والمصاريف المشتركة تُوزع بطريقة معلنة وحتمية؛ مجموع توزيعها يساوي مبلغها الأصلي.
- الضريبة لا تضاف إلى تكلفة الخامة ولا تستبعد منها بصورة عمياء؛ يلزم حسم المعالجة المدعومة. لا نفترض قابلية استرداد ضريبة.
- التكلفة الصفرية الصريحة مثل عينة مجانية تحتاج سببًا؛ خانة فارغة ليست صفرًا.

## 5. آخر سعر شراء والتحويل للوحدة الأساسية

مثال: ٥ كجم جبنة × ٢٠٠ جنيه = ١٬٠٠٠ جنيه. تكلفة الجرام ٠٫٢٠ جنيه.
استلام جديد بسعر ٢٥٠ جنيه/كجم يجعل التكلفة الحالية للجرام ٠٫٢٥ جنيه؛ وصفة تستهلك ١٠٠ جرام تكلفتها من الجبنة ٢٥ جنيه بعد التأكيد.

سجل التكلفة يحتفظ بالقيمة الدقيقة لكل وحدة أساسية، مصدرها وبند الفاتورة، هوية المستخدم، مستودعها، ترتيب التأكيد ووقت تسجيلها. كل تحديث حدث جديد، ويظل التاريخ قابلًا للقراءة.

- شراء ١٠ وحدات بـ٢٠٠، ثم ١٠ وحدات بـ٢٥٠: التكلفة الحالية ٢٥٠؛ لا تُحسب ٢٢٥.
- بيع سابق محفوظ بتكلفة ٢٠٠ يبقى كما هو. بيع جديد يتكلف ٢٥٠ حتى مع بقاء الكمية القديمة.
- سعر شراء أقل لاحقًا يحل محل الأعلى؛ لا سياسة «أعلى سعر تاريخي».
- ترتيب تأكيدات متزامنة وحفظ snapshot البيع يجب أن يكون حتميًا ومحمياً بالمعاملة والأقفال اللازمة.
- تكرار طلب تأكيد واحد لا ينشئ كمية أو حدث تكلفة إضافيًا.
- فاتورة قديمة التاريخ تؤكد اليوم لا تعيد كتابة تاريخ المبيعات. أثر التأكيد القديم التاريخ يُوضح للمستخدم حسب قرار D06.
- لا يُؤخذ متوسط أسعار سطور مختلفة للصنف نفسه خفية؛ D08 يحسم اختيار المصدر أو منع الحالة قبل تأكيدها.
- تغيير سعر البيع أو الوصفة لا يغيّر قيمة فاتورة الشراء ولا snapshots المبيعات السابقة.

### معنى قيمة المخزون

نحتفظ بقيمة الشراء الأصلية لكل فاتورة. ويمكن عرض «قيمة تقديرية بالأسعار الحالية» = الكمية الحالية × آخر تكلفة، مع تسمية واضحة.
ارتفاع آخر سعر لا ينشئ دفعًا أو مصروفًا أو قيد إعادة تقييم على المخزون القديم تلقائيًا. الفرق بين القيمة التاريخية والتقدير الحالي لا يُسجل كربح أو خسارة بيع.
تقييم المخزون المحاسبي وتتبع التكلفة الفعلية لكل دفعة خارج هذا الإصدار.

## 6. الرصيد الافتتاحي والتكلفة المجهولة

- المخزون الموجود قبل تفعيل الميزة يحتاج قيمة تكلفة افتتاحية موثقة أو يظهر غير معروف.
- إدخال تكلفة افتتاحية لا يزيد كمية المخزون ولا ينشئ فاتورة شراء وهمية أو سدادًا.
- المصدر يظل opening/manual seed، ولا يُعرض كأنه purchase invoice. تعديل seed تاريخ جديد بسبب واضح.
- شراء مؤكّد لاحق يحل محل seed حسب السياسة، دون تعديل مبيعات سابقة.
- البيع السابق لتفعيل snapshots يظهر «تكلفة تاريخية غير متاحة»؛ لا تعبئة رجعية بأحدث تكلفة.
- قد يكون المخزون سالبًا والتكلفة معروفة؛ سالب الكمية وحده لا يمحو السعر. عند غياب المصدر تكون التكلفة مجهولة.
- Snapshot بيع مجهول التكلفة لا يكتمل سرًا بعد شراء لاحق. أي تسوية تقديرية لاحقة تكون حدثًا معلنًا منفصلًا مع إبقاء الأصل وأثره على التقرير.

## 7. تكلفة المنتج والوصفة

- DIRECT: كمية صنف المخزون المستهلكة × آخر تكلفة للوحدة الأساسية في مستودع الاستهلاك.
- RECIPE: مجموع تكاليف المتطلبات المجمدة للصنف/الحجم والإضافات الفعلية والتغليف المعرّف ضمن الوصفة.
- احترام تحويل العبوة والكيلو/الجرام واللتر/المليلتر وكميات الإضافات وتبديل المكونات القائم.
- المعاينة تستخدم الوصفة الحالية والأسعار الحالية، وتسمى «تكلفة تقديرية حالية».
- تكلفة البيع تستخدم متطلبات الطلب المحفوظة، لا إعادة قراءة وصفة تغيرت بعد إنشاء الطلب.
- يمنع تأكيد البيع/قبول الطلب عند غياب تكلفة أي خامة أو مكون مطلوب. يمكن استعادة إيراد البيع التاريخي من الأسعار المحفوظة عند وجود تأكيد بيع؛ لا تُستكمل تكلفة تاريخية مجهولة بأثر رجعي.
- عدم وجود mapping أو وصفة تكلفة لا يساوي تكلفة صفرية. سعر البيع يبقى إعدادًا مستقلًا.

## 8. Snapshot البيع والإيراد

- تثبيت تكلفة كل بند ومكون عند استهلاك المخزون الفعلي في المسار القائم.
- يعترف POS بالإيراد عند تأكيد البيع، والطلب الإلكتروني عند قبوله؛ التحصيل لا يكرر الإيراد.
- Snapshot يحمل كمية الاستهلاك، تحويل الوحدة، مصدر وإصدار تكلفة كل مكون، التكلفة الدقيقة والإجمالي المقرب، المستودع، والوقت وأساس الحساب latest purchase.
- المصدر المالي للإيراد هو سعر البيع المحفوظ بعد توزيع الخصم؛ التحصيل النقدي تقرير مستقل ولا يُجمع مرتين مع البيع.
- خصم الطلب الإلكتروني يُوزع بنسبة lineTotal قبل الخصم، فيبقى مجموع إيرادات السطور مساويًا لمجموع البنود بعد الكوبون، دون رسوم التوصيل.
- يُسمح بترحيل الإيراد المحفوظ للمبيعات المؤكدة قبل snapshots. الطلب الإلكتروني المرفوض أو المعلّق والمبيعات الملغاة مستثناة؛ سطور التكلفة تظل مجهولة. عند غياب وقت قبول قديم، يستخدم الترحيل أول وقت مرحلة لاحقة متاح، ثم updatedAt.
- تعريف التقرير الأولي: صافي مبيعات المنتجات بعد الخصومات والمرتجعات، باستبعاد الضرائب والرسوم المحصلة للغير متى كانت مفصولة في العقد القائم.
- رسوم التوصيل والعمولات لا تُنسب تلقائيًا للمنتج؛ أي توزيع لها سياسة صريحة في P11.
- مجمل الربح الإداري = صافي مبيعات المنتجات − تكلفتها المحفوظة على أساس آخر شراء.
- نسبة الهامش = مجمل الربح ÷ صافي المبيعات × ١٠٠ عند صافي مبيعات موجب؛ غير ذلك يظهر غير منطبق.
- لا نسمّي الرقم «صافي ربح النشاط»؛ الإيجار والمرتبات والمصروفات العامة ليست ضمنه.

## 9. الاستعادة والمرتجعات والهالك والتحويل

- تخصيص قيمة الاسترداد اختياري في شاشة الاسترداد ويرتبط ببنود البيع وبالإيراد والتكلفة المحفوظين عند البيع؛ يمنع تجاوز الكمية أو القيمة المتبقيتين.
- استرداد مال دون رجوع خامات للمخزون يخفّض الإيراد ولا يستعيد الكمية أو التكلفة تلقائيًا. إرجاع المنتج المادي مسار منفصل عن الاسترداد المالي.
- الاستردادات غير المنسوبة لبنود تظهر منفصلة وتُخصم من مجمل ربح التاجر الإجمالي؛ لذلك قد لا يساوي مجموع صفوف المنتجات الإجمالي حتى تُنسب.
- تقسيم شيك أو نقل طاولة لا ينشئ بيعًا أو تكلفة إضافية.
- الهالك حركة خسارة مستقلة بتكلفتها وقت الحدث؛ التقرير يوضح موقع احتسابها لمنع طرحها مرتين.
- تحويل المستودعات لا يعتبر شراء أو بيعًا ولا يغير آخر سعر موحد للصنف؛ تُحفظ تكلفته على الحركة.
- مرتجع المورد يخفض مخزون المستودع المستلم ويرتبط برصيد ائتمان المورد، دون إنشاء استرداد نقدي. تصحيح الفاتورة مستند منفصل؛ لا يغير تكلفة أحدث مصدر إلا إذا كانت الفاتورة المصححة لا تزال ذلك المصدر.

## 10. سداد المورد

- تسجيل السداد الفعلي بمبلغه وتاريخه ووسيلته ومصدره ومن سجله، مع المرجع والحدود والصلاحيات.
- عرض غير مدفوع/جزئي/مدفوع مشتق من الحركات الفعلية والتسويات المرتبطة؛ السداد لا يُشتق من مجرد استلام المخزون.
- التكلفة والربح يتحددان بقيمة الشراء والبيع، لا بتاريخ دفع المورد.
- كل دفعة مرتبطة بحركة سحب نقدية/خزنة موجودة، من الفرع نفسه، ويُخصم المبلغ المتاح على الحركة لمنع إعادة تخصيصه. السداد لا ينشئ سحبًا جديدًا.
- قيد دفتر أستاذ كامل، تحصيل بنكي أو بوابة دفع آلية، والتقارير الضريبية القانونية خارج هذا الإصدار.

## 11. التقارير والصلاحيات

- المنتج/القسم التاريخي للمنيو/الفرع: كمية، إيراد معترف، استردادات، تكلفة مستهلكة، مجمل ربح، هامش، وبنود تكلفة مجهولة.
- التصنيف المنيوي والفرع يحفظان عند البيع؛ النقل اللاحق لا يغير التصنيف التاريخي. التصدير CSV يستخدم التجميع والفلاتر نفسيهما.
- الفلاتر والتصدير تعرض أساس latest purchase، العملة، النطاق الزمني، وتعريف تاريخ البيع وفق Africa/Cairo.
- التكلفة والربح صلاحيات منفصلة عن قدرة الكاشير على البيع؛ لا ترسل أسعار الموردين للواجهات العامة أو موظف غير مخول.
- الإجماليات التي تشمل تكلفة مجهولة توصف بوضوح بأنها غير مكتملة؛ التكلفة والربح والهامش لا تظهر كأرقام مكتملة لأي صف أو إجمالي يضم تكلفة مجهولة، وتظهر الصفوف المكتملة قبل الناقصة في الترتيب.

## 12. ملكية التنفيذ والحماية

| المجال | المالك المقترح داخل المعمارية القائمة |
| --- | --- |
| المورد وفاتورته وتصحيحها وسدادها | Purchasing؛ الربط المالي يعتمد على الخدمات المالكة للنقدية القائمة |
| الكمية وحركة الاستلام وآخر تكلفة موحدة للصنف عبر المستودعات | Inventory عبر public entry point؛ Purchasing يستدعي InventoryCostService ضمن transaction تأكيد الاستلام |
| المنتج والوصفة ومتطلبات استهلاكها | Catalog؛ لا يعتمد على Orders |
| تكلفة البيع المحفوظة، الإلغاء والمرتجعات وإسناد الإيراد | Orders داخل معاملات العمليات القائمة |
| عقود النقل والمخطط/migrations | packages/contracts وpackages/database |
| واجهات الإدارة | merchant-dashboard؛ لا حساب موثوقًا ماليًا في المتصفح وحده |

العقود والـschema والـmigrations المحددة موجودة في ملفات المصدر والـdatabase. كل تعديل لاحق يلتزم بملكية الوحدة والحدود والتبعيات أعلاه.
الحسابات العابرة للوحدات لا تستورد ملفات persistence خاصة من وحدة أخرى. لا دورات dependencies جديدة.
merchantId من جلسة المستخدم، وفحص tenant لكل مورد وصنف ومستودع وطلب. حفظ revisions وrequest idempotency والقفل وترابط الكمية والتكلفة.
migrations إضافية تحفظ البيانات الحالية؛ لا reset أو مسح أو تعديل migrations مطبقة. التقرير يعرض نقص تغطية التكلفة بوضوح، ولا تعتبر الفترات السابقة لتسجيل snapshots مكتملة.

## 13. شروط اكتمال الميزة كاملة

1. إدخال واستلام فاتورة مالية صحيحة؛ آخر سعر يتغير مرة واحدة عند التأكيد.
2. مثال ٢٠٠ → ٢٥٠ يمر لكل بيع جديد من الرصيد القديم والجديد؛ التاريخ السابق محفوظ، والانخفاض يعمل أيضًا.
3. تكلفة الوصفة والخيارات والوحدات صحيحة ومصادرها قابلة للتتبع.
4. الإيراد والتكلفة والاستردادات والهالك تتجمع دون تكرار أو تكلفة مجهولة كصفر.
5. سداد المورد يعكس معاملات فعلية، والصلاحيات تمنع كشف التكلفة أو تسجيل مال دون صلاحية.
6. التقارير والواجهة والتصدير تعرض نفس الأساس والأرقام؛ الحالات القديمة والناقصة معلنة.
7. جميع المراحل مغلقة بأدلة مراجعة يدوية، والقرارات المفتوحة حُسمت أو استُبعدت صراحة من النطاق المعتمد.
