## 1. Purpose and Scope

Merchant Management administers Waffarly's relationship with each merchant: onboarding, administrative information, owner access provisioning, approval where applicable, and approved suspension/reactivation operations. Each merchant operates within an isolated tenant/workspace.

The first release targets restaurants in Egypt. The product owner has selected this domain for discovery and explicitly requested **analysis of self-registration as an MVP candidate alongside manual Super Admin creation**. This does not approve self-registration delivery, finalize either workflow, or authorize implementation.

This overview identifies features, actors, recorded rules, candidate journeys, dependencies, security concerns, and focused decision questions. It does not create feature specifications, database models, lifecycle states, API contracts, or development tasks.

## 7. High-Level User Journeys

### 7.1 Manual Super Admin Creation — Recorded Route

1. Owner and Waffarly make direct contact; the channel may be WhatsApp but is not selected as an integration.
2. Administrator collects the four recorded restaurant/owner contact fields.
3. Administrator creates merchant and owner association. Historical SA-D03 treats this creation as approval.
4. Under the recorded credential route, administrator creates credentials, verifies the owner by call, and manually sends them privately. Owner-controlled setup remains a proposed alternative.
5. Subscription personnel follow the approved month-one condition: administrator activation after external collection confirmation. Owner cannot sign in/configure before activation under SA-D05.
6. Subsequent tenant operations are available only under their separately approved access, permission, and entitlement rules. Activation does not imply storefront publication or restaurant configuration exists.

Steps 4 and 5 are distinct dependencies; this sequence does not approve a required ordering of credential delivery versus collection/activation.

### 7.2 Self-Registration — PROPOSED MVP Candidate

1. Applicant submits the four required fields confirmed by MER-D03: restaurant name, restaurant contact number, owner name, and owner mobile number. Field validation, verification, and any optional fields remain OPEN.
2. Platform captures the application as a separate submission. Under MER-D02, this submission does not create an owner account for the applicant; owner account provisioning must wait until approval. If either the restaurant contact number or owner mobile number matches a prior rejected submission, the Super Admin can see all recorded data from each match, including the rejection reason (MER-D09–MER-D11). Phone normalization/equality, multiple-match handling, and history permissions remain OPEN; tenant/workspace creation timing remains OPEN.
3. The Super Admin personally reviews/checks the application (MER-D04). If approved, continue to the approved post-approval provisioning path. If rejected, the decision is final for that application (MER-D05), the Super Admin must provide a reason visible to the applicant (MER-D06), and any retry starts with a separate new application. Rejection criteria and reason-delivery/access mechanism, plus linkage/duplicate handling for a new application, remain OPEN.
4. Only after Super Admin approval is the owner account provisioned, as confirmed by MER-D02. The provisioning mechanism and whether it happens automatically or through a later administrator action remain OPEN. Merchant/workspace creation timing is also OPEN.
5. Owner dashboard access requires approval and any separately approved subscription/access prerequisites. Neither form submission nor password setup grants dashboard access.

No application status model, review deadline, automatic approval, reason format/constraints, secure reason-delivery/access mechanism, token mechanism, or post-approval dashboard access default is selected. MER-D05 means the rejected application cannot be corrected/reopened for resubmission; a retry is a new application. MER-D06 requires the rejection reason to be visible to the applicant, but how or when the applicant can access it remains OPEN and must respect application-only submission and the pre-approval Merchant Dashboard prohibition.

**Trade-off:** Self-registration may reduce repeated data entry by Waffarly staff, but introduces public submission abuse, duplicate identity handling, review queues, and applicant communication. Manual creation is narrower but requires operator effort and careful recipient verification. Analyze the release value and cost before deciding whether one or both routes ship.

### 7.3 Inspect or Correct Administrative Information — PROPOSED

Authorized administrator locates the correct merchant, sees only approved information, and makes only permitted corrections if editing is in scope. Subscription visibility does not imply permission to change plans. Field ownership, verification after changes, concurrency, and audit requirements remain OPEN.

### 7.4 Suspend or Reactivate a Merchant — PROPOSED MVP Actions

Authorized administrator identifies the target and requested action; backend evaluates approved authority and prerequisites, applies agreed restrictions/restoration, and records required history. Exact reasons, confirmations, notifications, session revocation, timing, and operational effects are OPEN.

**Practical Waffarly example:** A restaurant may have an order already accepted by its cashier when a restriction occurs. Whether staff can finish it and customers can view it must be decided explicitly. Restoring a suspended merchant must also respect any subscription restriction; it does not automatically renew the subscription.
