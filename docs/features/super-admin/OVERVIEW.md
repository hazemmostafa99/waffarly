## 1. Purpose

Super Admin is Waffarly's central platform administration system. It manages merchant relationships and platform configuration while merchant-facing applications operate each merchant's business within an isolated tenant/workspace.

This document provides a navigable feature inventory, conceptual boundaries, dependencies, scope distinctions, and a discovery roadmap. The owner has authorized the initial Templates & Design Library, monthly-plan administration, and hybrid Business Activities & Modules catalog slices; unrelated features and unresolved merchant-side decisions still need feature analysis and approval.

## 2. Platform Context

Waffarly is a multi-tenant, multi-merchant commerce and business management platform. Each merchant operates an isolated workspace. Super Admin controls approved platform administration; the Merchant Dashboard controls tenant business configuration and operations. The Next.js storefront presents a merchant's customer experience. React POS handles approved cashier workflows. These interfaces use backend-owned rules and shared commerce data.

| Concept                     | Responsibility / boundary                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Merchant                    | Business relationship managed by the platform; represents the tenant boundary in the current first slice. Ownership transfer and multiple businesses per identity remain OPEN. |
| Tenant/workspace            | Isolation boundary for merchant-owned users, configuration, and operational records. Logical isolation is required; the final enforcement/storage strategy is OPEN.            |
| Business Activity           | What kind of business the merchant operates. Restaurants are the only approved initial activity.                                                                               |
| Module                      | A defined platform capability. The final capability catalog and granularity are OPEN.                                                                                          |
| Activity/Module Association | Whether a capability applies to an activity; does not grant a commercial entitlement.                                                                                          |
| Plan Definition             | Commercial offer and approved feature/limit definitions; separate from a merchant's actual subscription.                                                                       |
| Merchant Subscription       | Merchant's relationship to an offer over time; lifecycle and collection are separate concerns.                                                                                 |
| Feature Entitlement         | Whether a tenant is commercially allowed to use a capability or limit.                                                                                                         |
| User Permission             | Whether an authorized person may perform an action; entitlement does not confer employee permission.                                                                           |
| Tenant Configuration        | How an available capability is configured for a particular merchant; configuration cannot bypass access rules.                                                                 |
| Storefront Template         | Activity-compatible storefront presentation; exact definition and relationship to plans are OPEN.                                                                              |

Catalog/Dynamic Product Builder, orders, branches, inventory, employees, and other shared domains remain separate operational responsibilities. Mentioning them here does not approve their complete MVP scope or give platform administrators unrestricted operational access.

### 2.1 Repository and implementation evidence

- **Actual structure:** `apps/api`, `apps/super-admin`, `apps/merchant-dashboard`, `apps/storefront`, and `apps/pos`; shared database, contracts, UI, and configuration packages under `packages/`. A pnpm workspace and Turborepo coordinate the repository; React dashboards currently use Vite. Local Docker PostgreSQL exists. These are observed initial choices, not a production topology decision.
- **Existing Super Admin UI:** [App.tsx](../../../apps/super-admin/src/App.tsx) supports sign-in/out, merchant creation/listing, temporary display of newly entered owner credentials, and first-month activation confirmation.
- **Existing backend:** [merchant controller](../../../apps/api/src/modules/super-admin/merchant.controller.ts) and [merchant service](../../../apps/api/src/modules/super-admin/merchant.service.ts) protect admin actions, validate inputs, create merchant/owner records together, and prevent repeated first-month activation.
- **Existing access enforcement:** [auth service](../../../apps/api/src/modules/auth/auth.service.ts) uses environment-configured admin identity, hashed passwords/session tokens, and HTTP-only cookie sessions. Owner login and profile access require a recorded first-month activation. These are initial implementation mechanisms, not final authentication policy.
- **Existing persistence/contracts:** [Prisma schema](../../../packages/database/prisma/schema.prisma) contains infrastructure marker, merchant, owner-account, and session models. [Shared contracts](../../../packages/contracts/src/super-admin.ts) cover this narrow slice. The one-owner-per-merchant constraint is an existing schema choice, not proof of an approved long-term identity model.
- **Not implemented in the merchant lifecycle slice:** recurring subscription records, renewal/expiry enforcement, suspension/reactivation, invitation/recovery, granular administrator RBAC, or a general administrative audit/history system. Monthly-plan definitions, the template library, and the hybrid activity/module catalog are implemented separately and recorded in their linked domain overviews. Activation records time and administrator; this is not a complete audit trail. Phone verification and external collection confirmation remain manual operator steps, not integrated verification services.

The activation timestamp is currently an access gate; it does not calculate a month end or enforce expiry. Current UI labels must not be interpreted as a complete subscription lifecycle. Review was static; no application, database, or business-flow tests were run for this documentation task. The inspected test file covers health endpoints, not the merchant onboarding lifecycle.

**Monthly-plan implementation update — PS-D04:** [Plans UI](../../../apps/super-admin/src/Plans.tsx), authenticated plan routes, a `MonthlyPlan` table, shared contracts, and plan API tests now exist. Validation/build/migration evidence is recorded in the [Monthly Plan specification](plans-subscriptions/MONTHLY_PLAN.md). This update does not add merchant assignment, recurring coverage, or collection.

### 3.1 Plans & Subscriptions

**Domain discovery:** [Plans & Subscriptions overview](plans-subscriptions/OVERVIEW.md). PS-D01 confirms the owner's selection of a discovery document, with onboarding/access dependencies coordinated through Merchant Management. PS-D02 confirms multiple monthly plans at launch; exact count, names, differences, pricing, and governance remain OPEN. Other commercial rules and expanded delivery scope remain OPEN.

**Current selected feature:** [Monthly Plan administration](plans-subscriptions/MONTHLY_PLAN.md), SA-PS01. PS-D03 focuses on a basic monthly offer first; PS-D04 explicitly authorizes documentation and app implementation. Authenticated create/list/edit is implemented with administrator-entered name, monthly price, currency, and description. The multiple-plan direction is preserved; assignment, tier differences, recurring access, and collection remain separate work.

- **Purpose:** Define commercial offers and administer merchant subscription relationships.
- **Responsibilities / high-level capabilities:** Plan creation/editing, pricing and billing-period configuration, plan assignment, subscription visibility, feature/limit entitlements, and approved lifecycle/collection operations. Keep plan definitions, subscriptions, entitlements, lifecycle, and collection logically separate.
- **MVP considerations:** Multiple monthly subscription plans (PS-D02) and no payment-provider integration are CONFIRMED. Recorded SA-D06 confirms manual first-month activation after external collection confirmation, subject to SA-R03 reconciliation. This does not settle exact plan count, names, differences, prices, renewal, expiry, suspension, or entitlements.
- **Future capabilities:** Other commercial models, add-ons, invoicing, and provider collection require separate decisions; commission/hybrid billing is deferred in the MVP proposal.
- **Dependencies:** Merchant identity/tenant boundary, capability definitions if plans gate modules, authorization, and audit policy. Template entitlements are conditional on a later decision.
- **Unresolved questions:** What offers and limits are necessary? Is a configurable plan catalog required at launch? What proves collection, when does a month start/end, and what happens at renewal/expiry or a plan change?

After selecting feature discovery documentation (TDL-D01), the owner authorized the first working slice. Super Admin manages two initial restaurant designs; a merchant owner can select one, add a logo, and set a color. Public storefront rendering and publication remain OPEN.

- **Purpose:** Maintain activity-appropriate storefront designs available to merchants.
- **Responsibilities / high-level capabilities:** Template library and metadata, activity compatibility, merchant availability/selection, and approved branding/customization controls. Merchant customization belongs in merchant-facing flows; platform availability belongs in Super Admin.
- **MVP considerations:** The activity-associated design library is CONFIRMED platform vision in PROJECT_OVERVIEW.md section 4.1. TDL-D02 confirms two full restaurant designs, owner selection, a tenant logo, and an accent color; the initial library and owner settings are implemented. Broader release scope and public rendering/publication remain OPEN. The Next.js choice does not establish a template engine.
- **Future capabilities:** Templates for future activities and broader visual customization, only when approved. A theme marketplace is not an implied requirement.
- **Dependencies:** Definition of a template, supported activities, storefront rendering/publishing behavior, tenant branding, and optionally entitlements.
- **Unresolved questions:** Multiple activities per design? Shared design versioning and rollout? Public storefront availability and publication? Accessibility, language, and responsive requirements? Plan inclusion remains undecided.

### 3.3 Business Activities & Modules

- **Purpose:** Describe supported business types and their applicable platform capabilities.
- **Responsibilities / high-level capabilities:** Activity definitions, module definitions, activity/module associations, compatibility/dependencies, and capability availability. Commercial entitlement and person-level permission remain separate decisions.
- **MVP considerations:** Restaurants only. Catalog, orders, POS, inventory, employees, branch management, and restaurant extensions are conceptual examples, not approved module definitions. The Dynamic Product Builder is CONFIRMED cross-activity platform capability; exact restaurant MVP rules remain OPEN.
- **Future capabilities:** Clothing, supermarket, electronics, and other approved activities using shared core concepts plus specialized rules. No arbitrary runtime backend installation or dynamic database schema creation is assumed.
- **Dependencies:** Stable capability meaning, shared commerce boundaries, actual implemented functionality, and later plan entitlement mapping. Activity/module definitions describe available software; metadata alone cannot create functionality.
- **Initial implementation:** [Business Activities & Modules](activities-modules/OVERVIEW.md) records confirmed hybrid governance: code defines supported activities/capabilities; admins edit catalog descriptions and restaurant applicability. The initial registry represents merchant profile and storefront design/branding. Applicability is metadata and does not change merchant access.
- **Unresolved questions:** Broader operational module granularity, future dependency rules, merchant activity changes/multiple activities, and runtime availability/entitlement consumption.

**Practical trade-off:** A shared Product Core can support a burger's modifiers and a shirt's sizes while specialized rules handle kitchen dispatch or exchanges. Separate activity backends would duplicate shared commerce behavior; a universal model containing every future industry rule would add premature complexity. Preserve clean extension boundaries and specify only restaurant behavior now.

**Governance decision (AM-D01, CONFIRMED 2026-10-13):** The product owner selected hybrid management. Code owns supported definitions and permanent keys; dashboard edits maintain descriptions and restaurant applicability. Renaming a module does not deploy its backend functionality. Broader module scope and release/versioning policy remain OPEN.

### 3.4 Merchant Management

**Domain discovery:** [Merchant Management overview](merchants/OVERVIEW.md). The owner confirmed self-registration MVP analysis alongside manual creation (MER-D01), application-only submission with owner account provisioning after approval (MER-D02), the same four required contact fields as manual creation (MER-D03), manual Super Admin review with no automated verification (MER-D04), final rejection with retry through a new application (MER-D05), a required applicant-visible free-text rejection reason (MER-D06/MER-D08), and reviewer visibility of all prior rejected application data including its reason when either phone number matches (MER-D09–MER-D11). Phone normalization and history display details remain OPEN. The reason access/delivery decision is deferred until applicant-tracking UX is defined (MER-D07). Final release scope remains OPEN.

- **Purpose:** Manage platform merchant records, onboarding, ownership/access provisioning, and approved lifecycle administration.
- **Responsibilities / high-level capabilities:** Creation, listing/detail, administrative information maintenance, application review where applicable, suspension/reactivation, subscription visibility, and authorized access management.
- **MVP considerations:** Existing SA-D01–SA-D08 record the historical manual route, four contact fields, approval by creation, admin-created owner credentials, pre-activation login prohibition, and manual month-one activation. MER-D01 reopens self-registration for MVP analysis; MER-D02–MER-D06/MER-D08–MER-D11 define application-only submission, review responsibility, rejection with a required applicant-visible free-text reason and retry via a new application, and reviewer access to all prior rejected application data including its reason when either phone field matches. MER-D07 defers reason delivery/access until applicant-tracking UX is defined. Phone normalization, multiple-match presentation, and history privacy remain OPEN. These decisions do not approve delivery or replace credential/activation rules. SA-R01–SA-R03 track remaining reconciliation.
- **Future capabilities:** Additional administrative actions, ownership transfer, and broader owner membership only after discovery. Self-registration is now an MVP discovery candidate, with delivery scope OPEN. No WhatsApp API requirement exists.
- **Dependencies:** Authentication/authorization, owner identity and provisioning, tenant isolation, subscription access conditions, input validation, and audit policy. Activity selection is conditional; the initial activity is restaurants.
- **Unresolved questions:** Reconcile the current direction; field validation/duplicates/corrections; owner setup/recovery; ownership/membership; suspension authority, reason, notice, and effects on staff, storefront, active orders, and retained data.

Creation, application review, approval, operational activation, suspension, reactivation, and subscription access are distinct concepts. The recorded manual route deliberately treats creation as approval, with subscription activation separate; it does not define a universal lifecycle. No state names or transition graph are introduced here.

## 4. Cross-Cutting Concerns

These support all four domains and do not add a fifth major domain.

| Concern                        | Requirement / decision boundary                                                                                                                                                                                                                                                                 |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication                 | Protect platform access. Existing cookie sessions are an initial mechanism; final admin identity, recovery, session policy, and any additional safeguards are OPEN.                                                                                                                             |
| Authorization / RBAC           | Enforce actions and visibility server-side. Platform administrator roles and permission matrix are OPEN; an admin title does not automatically authorize tenant operational access or impersonation.                                                                                            |
| Account security               | Do not store/log plaintext credentials. Historical credential delivery is recorded under SA-R02; owner-controlled setup is a PROPOSED alternative. Recovery, reset, voluntary change, and disclosure controls need analysis.                                                                    |
| Tenant isolation               | Validate trusted tenant context and tenant-safe references. Platform configuration is distinct from tenant-owned records. Final isolation mechanisms, including any row-level security, are OPEN.                                                                                               |
| Entitlement enforcement        | Backend checks tenant capability eligibility independently of user permission. Feature definitions, limits, and restriction behavior require approval.                                                                                                                                          |
| Validation / errors            | Backend owns validation and business rules; UI feedback supports it. Current checks are implementation evidence, not approval of every format/limit. Define safe validation, forbidden, conflict, and failure behavior per feature.                                                             |
| Audit / administrative history | Record approved sensitive actions with actor, target, action, outcome, and time, without secrets. Event list, retention, visibility, and any history UI are OPEN. Technical logs are not a substitute for a business audit trail.                                                               |
| Transactional consistency      | Coordinate related approved changes and define retry/concurrency behavior. For example, creating a restaurant must not leave an unusable owner relationship; recording activation must not claim unverified payment-provider collection. Exact consistency boundaries belong in feature design. |

Auditability, isolation, backend ownership, separation of concerns, and server-side permission/entitlement enforcement are platform principles. They do not approve specific services, packages, role names, storage engines, or every supporting screen.

## 6. Domain Relationships

The following relationship is conceptual, not a finalized schema or a guaranteed ordering of setup steps:

```text
Business Activity
  -> Applicable Modules
  -> Plan Entitlements (commercial eligibility must also be defined)
  -> Merchant Subscription (applicable offer/access rules)
  -> Merchant Available Capabilities
```

Activity compatibility and commercial eligibility constrain availability independently. An entitled capability must also exist in deployed software, apply to the merchant's activity, and satisfy approved merchant/subscription access rules. An employee then needs the relevant permission; tenant configuration controls approved behavior within those boundaries. Whether every compatible capability is plan-controlled remains OPEN.

**Example:** A restaurant may be compatible with inventory, but that does not establish its plan inclusion, restaurant MVP scope, or a cashier's stock-adjustment permission. Likewise, a subscription restriction must not be treated as merchant rejection or deletion; its effect on an accepted kitchen order needs a separate decision.

The template relationship is separate:

```text
Business Activity -> Compatible Storefront Templates
Compatible Templates + Platform Availability -> Merchant Template Choices
Merchant Selection + Approved Branding Configuration -> Storefront Presentation
```

Plan entitlements enter template eligibility only if explicitly approved. A template selection must not automatically enable backend operational modules, and a visual layout does not define product/order business rules.

## 11. Implementation Roadmap

**PROPOSED high-level sequence only; no tasks, estimates, schemas, or contracts are approved by this sequence.**

1. Reconcile recorded decisions and agree the minimum merchant/access and subscription boundaries.
2. Specify approved platform authentication/permissions, tenant isolation, audit, validation, and consistency requirements alongside the selected feature.
3. Design and then, only when authorized, adapt or extend the existing merchant/owner slice to the approved requirements.
4. Design approved monthly plan/subscription administration and entitlement enforcement using only the necessary capability definitions; define renewal/expiry before claiming recurring subscription support.
5. Add activity/module and template administration only to the extent their separately approved MVP needs require. Broader catalogs and future activities follow separate approval.
6. Validate approved flows, operational effects, access boundaries, and production requirements against feature acceptance criteria.

Feature-based modular boundaries, backend-owned behavior, high cohesion/low coupling, and shared core models guide later design. A modular backend is a proposed direction; no microservices split, runtime plugin engine, or speculative future-industry implementation is introduced. Domain selection starts discovery and does not authorize implementation.
