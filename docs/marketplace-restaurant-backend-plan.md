# خطة تجهيز Backend المطاعم لمطابقة واجهة Marketplace

التاريخ: 2026-11-11. الحالة: خطة تنفيذ مقترحة؛ لم يبدأ التنفيذ.

## النتيجة المطلوبة

نحافظ على تصميم ومكونات Marketplace الحالية، ونجهز Backend قادرًا على تقديم
نفس محتوى المطاعم والمنيو والمنتجات والاختيارات والصور والأسعار والترتيب.
بعد التنفيذ يصبح مصدر المحتوى قاعدة البيانات والقراءات العامة، بدل الملفات
المحلية. توصيل الواجهة فعليًا مرحلة لاحقة، ولا يدخل ضمن كتابة هذه الخطة.

مرجع الفجوات: [المراجعة التفصيلية](marketplace-restaurant-data-gap-review.md).
المراجعة السابقة للكود والمخطط والـseed؛ سجلات قاعدة البيانات العاملة لم تُجرد.

## 1. تثبيت نسخة المحتوى المطلوب مطابقتها

مصدر حزمة الاستيراد هو الناتج النهائي لهذه المصادر معًا:

- `apps/storefront/src/features/marketplace/data/reference.json`.
- `apps/storefront/src/features/marketplace/data/merchant-detail-scenarios.json`.
- `apps/storefront/src/features/marketplace/data/restaurant-scenarios.ts`.

لا يكفي استيراد reference.json وحده: المنيو والأوصاف والاختيارات جزء منها مولّد.
تُحفظ نسخة محتوى ثابتة ذات إصدار ومعرف مصدر لكل سجل، ثم لا يعتمد خادم الإنتاج
على استيراد ملفات TS من تطبيق الواجهة أثناء التشغيل.

الحزمة الحالية المستهدفة: 12 مطعمًا، و41 صنفًا موزعًا: 8 في بيت البرجر، و3 في
كل مطعم آخر. تحفظ الأسماء العربية والأوصاف والصور المستخدمة بالفعل، حتى
الأسماء التي تتضمن «تجريبي». لا نكتب منيوهات بديلة ولا نستخدم seed الكتالوج
القديم ذي الأسماء والأسعار والصور المختلفة.

يشمل بيان المطابقة: الاسم، وصف/نوع المطعم، الشعار والغلاف، شارة العرض والتقييم
المعروضان، نطاق الوقت، أقسام المنيو وترتيبها، كل صنف ووصفه وصوره وسعره وتوفره،
الأحجام والإضافات وأسعارها وترتيبها، الاختيارات الافتراضية، وإعدادات السيناريو.
حقول تنسيق العرض مثل displayPrice لا تصبح أعمدة مستقلة لمجرد وجودها بالـfixture.

**معيار الاكتمال:** بيان استيراد واضح لكل سجل وعلاقة، مع فصل المحتوى المرجعي
عن أي بيانات تشغيلية إضافية لا يحتويها المرجع.

## 2. ملف المطعم وصورته العامة

يعاد استخدام Merchant وهوية التاجر ونشاط restaurant؛ لا نبني نظام تجار بديلًا.
نضيف إعدادات عرض مرتبطة بالتاجر ضمن ملكية Storefront الحالية:

| البيانات            | العمل المخطط                                                                  |
| ------------------- | ----------------------------------------------------------------------------- |
| الاسم والهوية       | إعادة استخدام Merchant.name/id وstorefrontSlug؛ دعم handle الموجود عند الحاجة |
| وصف ونوع الأكل      | محتوى عربي مطابق لـmeta، وتصنيفات نوع أكل منظمة للبحث والفلاتر                |
| الشعار والغلاف      | علاقات ميديا tenant-scoped؛ نحتفظ بآلية logoData القديمة للتوافق              |
| النص البديل للصور   | حفظ النص المرجعي حيث يوجد؛ fallback مشتق من الاسم                             |
| ظهور Marketplace    | حالة نشر مستقلة وترتيب عرض؛ التاجر المغلق يمكن أن يبقى ظاهرًا                 |
| التقييم وشارة العرض | حفظ القيم المرجعية مع مصدر demo واضح؛ لا تقديمها كتقييمات موثقة أو عروض مطبقة |
| ترتيب الهوم/القائمة | ترتيب ثابت يحافظ على ترتيب reference، بدل ترتيب الإنشاء أو الاسم فقط          |

الشعار والغلاف في كارت المطعم يظلان نفس الصور. لا نعيد بانر المنيو الذي أزاله
المستخدم، ولا نضيف إعداد قالب جديد يغير تصميم Marketplace. ألوانه ومقاساته
تظل مسؤولية الواجهة.

**معيار الاكتمال:** يمكن تكوين كارت المطعم وملخص صفحته بنفس المحتوى من البيانات
المحفوظة، دون fallback لصورة أخرى أو نص hardcoded مفقود من الخادم.

## 3. مواعيد العمل وحالة استقبال الطلبات

نضيف إعدادات على مستوى المطعم في المرحلة الأولى، دون تغيير مواعيد POS أو
اختراع توجيه فروع تلقائي. يتضمن النموذج:

- timezone؛ القيمة الافتراضية للمطاعم المصرية Africa/Cairo.
- جدول أسبوعي: لكل يوم مغلق أو فترات عمل، مع دعم أكثر من فترة.
- فترات تتجاوز منتصف الليل، مثل 18:00 إلى 02:00 في اليوم التالي.
- استثناءات بتاريخ محلي: إجازة أو ساعات خاصة، بأولوية على الجدول الأسبوعي.
- إيقاف استقبال الطلبات يدويًا، مع سبب اختياري ورسالة عامة مناسبة.
- إمكانية تشغيل دائم صريحة بدل اعتبار الجدول الفارغ «مفتوحًا» دون قصد.

الخادم يحسب في القراءة: هل المطعم مفتوح الآن، وهل يقبل الطلبات، وسبب التوقف،
وأقرب تغيير حالة عند توفره. نفصل فتح المحل عن قبول الطلبات وعن نشره في القائمة.
فحص الطلب يعيد تقييم الحالة وقت التأكيد، حتى لو فتح العميل الصفحة قبل الإغلاق.
انتهاء الاشتراك أو عدم أهلية البيع لا يتحول إلى ادعاء بأن ساعات المحل انتهت.

المراجع الحالية لا تحتوي ساعات عمل فعلية. لنسخة المطابقة نستخدم إعدادًا
تجريبيًا معلنًا يحافظ على حالة العرض الحالية: 11 مطعمًا مفتوحًا وجرين بايتس
مغلقًا. أي جدول أسبوعي مضاف لهذه النسخة مثال محلي، وليس معلومة مستخرجة عن
مطعم حقيقي. الجدول الفعلي يُدخل من الإدارة عند التشغيل الحقيقي.

**معيار الاكتمال:** نتيجة واحدة متسقة للقراءة وإنشاء الطلب، تشمل منتصف الليل
والاستثناءات والإيقاف اليدوي، مع بقاء المنيو قابلًا للتصفح عند الغلق.

## 4. التوصيل والاستلام والأسعار والوقت

| الاحتياج          | نطاق المرحلة الأولى                                                              |
| ----------------- | -------------------------------------------------------------------------------- |
| أنواع الاستلام    | تشغيل/تعطيل delivery وpickup لكل مطعم                                            |
| رسوم التوصيل      | مبلغ ثابت للمطعم، مع قابلية تعريف مناطق توصيل مسماة برسوم مستقلة                 |
| تغطية التوصيل     | منطقة خدمة معلنة واختيار منطقة مدعومة إذا فُعل تعدد المناطق                      |
| الحد الأدنى       | مبلغ سلة الأصناف قبل رسوم التوصيل، يطبق على delivery فقط مثل الواجهة الحالية     |
| الوقت المتوقع     | حد أدنى وأقصى بالدقائق، يحافظان على النطاق المرجعي مثل 25–35 دقيقة               |
| نطاق سعر «من/إلى» | يحسب من رسوم المناطق المدعومة عند اختلافها، وليس نصًا منفصلًا يناقض السعر الفعلي |
| الاستلام          | بدون رسوم توصيل، مع قواعد إتاحته للمطعم                                          |

نسخة reference تبدأ برسوم ثابتة 25 جنيهًا وحد أدنى 100 جنيه، وبنفس نطاق وقت
كل مطعم. لا نختلق أسعار مسافات أو رسوم مناطق غير موجودة في المرجع. لو احتجنا
عرض نطاق رسوم في مثال ثابت يكون الحدّان 25، وليس نطاقًا عشوائيًا.

تعدد المناطق إضافة تشغيلية لا يلزم تفعيلها في نسخة المطابقة. عند تفعيله لا
يمكن معرفة رسم دقيق من عنوان نصي فقط؛ يلزم اختيار منطقة أو حل تغطية معتمد.
التسعير بالكيلومتر والخرائط وتتبع المندوب خارج هذه المرحلة.

**معيار الاكتمال:** سعر القراءة/الملخص يطابق السعر الذي يعيد الخادم احتسابه
ويحفظه في الطلب، مع رفض منطقة أو نوع استلام غير مدعوم بوضوح.

## 5. المنيو والأصناف والـvariants والإضافات

نعيد استخدام Catalog الحالي: Product، Category، ProductImage، ProductVariant،
ModifierGroup والتعيينات الخاصة بالمنتج. نضيف فقط ما ينقص العرض:

- ترتيب أقسام المنيو وترتيب الأصناف داخل القسم.
- قرار صريح لقسم العرض الأساسي عند وجود صنف في أكثر من Category، مع حفظ
  التصنيفات الأخرى؛ لا نكرر الصنف دون قصد أو نربط القسم بالاسم النصي.
- قراءة تعرض غير المتاح مؤقتًا مع availability، وتخفي المؤرشف وغير المنشور.
- قراءة عامة مباشرة لصنف داخل مطعمه، تدعم الرابط المباشر وnot-found.
- إعدادات العرض الضرورية كالأوصاف والصور والنصوص البديلة إن لم يكفِ الموجود.
- تضمين الاختيارات الفعلية لكل صنف، لا فرض الحجم والجبنة على كل المنيو.

الأحجام تستخدم variants بأسعار كاملة، مثل عادي 185 وكبير 225؛ نفس زر الواجهة
يمكنه إظهار فرق +40. الإضافات تستخدم modifiers، مثل جبنة +20 وصوص +10.
المشروبات تبقى بنفس أمثلتها: حجم كبير +15 وحليب +5 وكراميل +10.

الأول الافتراضي هو أول variant متاح حسب ترتيب ثابت؛ يرسل العميل variantId
بوضوح. الاختيارات المطلوبة ذات الاختيار الواحد تُضبط افتراضياتها بما يطابق
أول خيار متاح. الإضافات الاختيارية في نسخة المرجع تبدأ دون تحديد، ويحفظ
defaultSelected المناسب على تعييناتها. المنتجات بلا variants أو بلا إضافات
تظل صالحة، والمجموعات ذات min/max المختلفة تحافظ على قواعدها الحالية.

لا نكرر تكلفة الحجم كـvariant وmodifier معًا. السعر النهائي يحسبه Catalog؛
الواجهة تعرضه بنفس التصميم. تُحترم صلاحية الإضافات واختلاف أسعارها حسب الحجم.

**معيار الاكتمال:** نفس أسماء وترتيب وأسعار الأحجام والإضافات، ونفس الصنف
غير المتاح، وتطابق مثال كبير + جبنة = 245 جنيهًا للبرجر الكلاسيك.

## 6. القراءات العامة وإدارة الإعدادات

نعمل داخل Storefront لتركيب قراءة Marketplace، وCatalog لقراءة الأصناف.
أسماء المسارات التالية تُحسم وقت كتابة العقود؛ المطلوب هو القدرات التالية:

1. قائمة مطاعم منشورة: pagination محدودة، بحث، نوع أكل، مفتوح، وترتيب.
2. تفاصيل مطعم: هويته وصوره وملفه العام وحالة التشغيل وقواعد الاستلام.
3. أقسام منيو وأصناف بصفحات وتصفية وبحث، تشمل حالات عدم التوفر المطلوبة.
4. تفاصيل صنف عام داخل تاجر محدد، وصوره وأحجامه ومجموعاته.
5. إعادة استخدام quote الحالي للمنتج، وتكميله بتسعير سلة/رسوم توصيل عند الطلب.
6. owner read/update لإعدادات الملف والتشغيل والمواعيد والتوصيل، مع revision
   والتحقق من الملكية ونسبة التعديل لصاحبه.
7. صلاحية إدارة النشر من جهة الإدارة وفق أدوار المشروع الحالية؛ لا كشف قوائم
   الإدارة أو بيانات المالك للزائر العام.

نحافظ على استجابات `/catalog/stores/:slug` وقراءات POS القديمة، ونضيف القدرات
المطلوبة بتوسعة متوافقة أو قراءة Marketplace مستقلة عند اختلاف السلوك.
لا نسحب كتالوج كل التجار من المتصفح لبناء البحث العام.

تحديث شاشة إدارة المطعم لتعبئة هذه الحقول مطلوب لاحقًا لاستخدامها عمليًا،
لكن هذه الحزمة تخطط أولًا لعقود وأعمال Backend. إدارة Product Builder الحالية
يعاد استخدامها للأصناف بدل بنائها مرة أخرى.

**معيار الاكتمال:** جميع حقول الواجهة لها قراءة عامة ومصدر كتابة مسؤول، دون
تسريب اتصال المالك أو المخزون الداخلي أو حسابات الموظفين أو أسرار الإدارة.

## 7. ربط قواعد التشغيل بالتسعير والطلب في الخادم

جاهزية الـBackend لا تكتمل بحفظ رسوم أو ساعات للعرض فقط. نمد Orders بما يلزم:

- إعادة فحص نشر/أهلية المطعم، قبول الطلبات وساعات العمل، نوع الاستلام والمنطقة.
- إعادة تسعير الأصناف والأحجام والإضافات وتطبيق الحد الأدنى ورسوم التوصيل.
- حفظ subtotal وdeliveryFee وtotal وسياسة/منطقة التوصيل المستخدمة كسجل ثابت.
- التقاط إعدادات الرسوم داخل معاملة الطلب، وفحص revision/قفل مناسب يمنع أن
  يتأكد الطلب بسعر مختلف صامتًا عن آخر عرض وافق عليه العميل.
- حماية إعادة محاولة إنشاء الطلب بمعرف طلب idempotency محدد النطاق وبصمة
  للمحتوى؛ نفس المحاولة تعيد نفس النتيجة ولا تنشئ طلبًا ثانيًا.
- الحفاظ على معاملات المخزون وsnapshots والاشتراكات الحالية، وعزل بيانات كل تاجر.
- تحويل أسباب الرفض إلى نتائج يمكن للواجهة عرضها دون تغيير تصميمها.

تحديد فرع قبول الطلب والتعامل مع المخزون الحالي يظل متوافقًا مع التدفق
الموجود؛ لا نضيف توجيه فروع تلقائيًا ضمن إعدادات المواعيد. سجل العميل والتتبع
العام والدفع الإلكتروني لهم حزمة مستقلة، ولا نعتبر endpoints الموظفين بديلًا لها.

**معيار الاكتمال:** إجمالي محفوظ موثوق، ورسوم لا تعتمد على المتصفح، ورفض
الإغلاق/التغطية/الحد الأدنى من الخادم، وتكرار آمن للمحاولة.

## 8. استيراد نسخة مطابقة من البيانات والصور

يُجهز importer مخصص لهذه الحزمة، مستقل عن seed الكتالوج الحالي:

1. ربط كل مفتاح مرجعي بمعرف Merchant/Product/Category/Variant/Modifier/Media
   حقيقي؛ الربط ليس بالاسم القابل للتعديل وحده.
2. استهداف بيئة تطوير/عرض ونطاق تجار محدد. يمكن إنشاء تجار عرض مخصصين
   الاثني عشر أو ربطهم بتجار محددين صراحة، دون استبدال محتوى تاجر فعلي.
3. أي حقول تقنية إلزامية لتاجر العرض تُملأ بقيم تجريبية معلنة؛ لا نسجل بيانات
   اتصال حقيقية أو كلمات مرور ثابتة ضمن حزمة المحتوى.
4. تسجيل/نسخ الصور نفسها: صورة الغلاف والشعار وصورة الصنف وكل صورة إضافية.
   نحفظ عنوان المصدر ومعرفه والبصمة حيث نملك نسخة ملف، ونعيد استخدام الأصل
   المشترك مع علاقات صحيحة لكل tenant؛ لا نولد صورًا بديلة.
5. عند الاكتفاء بروابط الصور الحالية تبقى قيمها مطابقة؛ لو نسخناها للتخزين
   الخاص بنا يتغير الرابط فقط وتبقى نفس الصورة والمحتوى البصري. فشل جلب أصل
   يُسجل كخطأ واضح، ولا يعوض بصمت بصورة placeholder ثم يعلن نجاح المطابقة.
6. استيراد أسماء/أوصاف/أسعار/أقسام/ترتيب/توفّر واختيارات دون إعادة صياغة.
7. حفظ التقييم والعرض كمرجع تجريبي، حتى لا يتحول «توصيل مجاني» في كارت تجريبي
   إلى قاعدة مالية تناقض رسم 25 المحفوظ في السيناريو الحالي.
8. جعل الاستيراد قابلاً للإعادة دون تكرار، ومُصدرًا بتقرير تغيرات ومعرفات
   مستوردة. إعادة التشغيل لا تعيد تهيئة سجلات غير تابعة لهذه الحزمة.

نحتاج التمييز بين عرض داتا المرجع حرفيًا وتشغيلها كتجارة حقيقية: المرجع نفسه
فيه محتوى تجريبي وعروض غير مطبقة حسابيًا. نحفظه كما هو في نسخة العرض، ونمنع
اعتماد تلك الادعاءات أو حالات الفتح المصطنعة كحقائق إنتاج دون إعداد حقيقي.

**معيار الاكتمال:** 12 مطعمًا و41 صنفًا، نفس النصوص والصور والأسعار والترتيب
والاختيارات والتوفر، مع سجل ربط واضح وعدم تكرار بعد إعادة الاستيراد.

## 9. توزيع الملكية ومنع تضارب الوحدات

| الوحدة          | المسؤولية                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------- |
| Merchants       | هوية التاجر ونشاطه والـslug/handle وعلاقته بالحساب                                        |
| Storefront      | ملف العرض والنشر وإعدادات تشغيل المتجر العامة، الساعات والتوصيل، وتركيب قراءة Marketplace |
| Catalog         | المنتجات والتصنيفات وترتيب المنيو والأحجام والإضافات والتوفر وتسعير الصنف                 |
| Orders          | تطبيق أهلية وقواعد الطلب، الإجماليات والرسوم وidempotency وsnapshots والمعاملة            |
| Media / Storage | تسجيل وحفظ الأصول والتحقق من الملكية والروابط                                             |

Storefront يوفر قراءة أهلية/إعدادات مقصودة عبر index.ts كي تستخدمها Orders؛
لا نجعل Catalog يعتمد على Storefront أو Orders. أي اعتماد جديد يُسجل في
وثيقة المعمارية وقواعد imports. تحديثات الإعدادات revisioned، علاقات الميديا
والأصناف merchant-scoped، والتغييرات الهيكلية عبر migrations إضافية.

للشراء قبل اكتمال قواعدها وبياناتها اللازمة.

## 11. حدود المطابقة والتسليم

بعد هذه الحزمة يكون Backend مجهزًا لتقديم نفس محتوى الصفحات الحالية؛ تحويل
مصدر الواجهة من mock إلى API خطوة ربط منفصلة. أبعاد الكروت والبوب أب وألوان
الموقع لا تنتقل لقاعدة البيانات ولا يعاد تصميمها.

تفاصيل ليست ضمن هذه الحزمة: بوابة دفع إلكتروني، نظام مراجعات مستخدمين كامل،
محرك خصومات متكامل، خرائط ومسافات، تطبيق مندوب، حسابات عميل وسجل طلباته
وتتبع عام محمي. تُسجل كمتطلبات لاحقة قبل الادعاء بأن الرحلة التجارية كلها حية.

طبقًا لتوجيه المستخدم: لا تشغيل tests أو typecheck أو lint أو build أثناء هذا
العمل ما لم يطلبها لاحقًا. معايير الاكتمال أعلاه تصف النتائج المطلوبة؛ ليست
ادعاء بأن تحققًا آليًا أو تشغيلًا فعليًا قد تم. يسلّم كل جزء مع خطوات مراجعة
يدوية وبيان صريح لما بقي دون تحقق، بدل إسقاط القواعد بسبب عدم تشغيل الاختبارات.
