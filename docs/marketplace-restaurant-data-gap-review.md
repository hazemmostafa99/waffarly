# مراجعة توافق بيانات المطاعم مع واجهة Marketplace

التاريخ: 2026-11-11.

هذه مراجعة للكود، مخطط البيانات، العقود العامة، وملفات البيانات المحلية والـseed.
لم تتم قراءة سجلات قاعدة بيانات عاملة أو استدعاء API؛ وجود حقل في المخطط لا
يثبت أن بياناته مُدخلة عند تاجر بعينه. لم تتغير الواجهة أو العقود أو قاعدة
البيانات، ولم يُنفذ ربط أو seed أو tests أو typecheck أو lint أو build.

## القرار الذي تحافظ عليه المراجعة

واجهة Marketplace الحالية مرجع العرض: نفس الهوية والمكونات والمقاسات، ونفس
أماكن الاسم والصورة والوصف والاختيارات. نجهز البيانات لتغذيها، ونغير منطق
مصدر البيانات وتحويلها دون إعادة تصميم الواجهة. الأسعار والتوفر والطلبات
الفعلية تظل مسؤولية الخادم عند بدء الربط لاحقًا.

المطعم في النظام الحالي Merchant بنشاط restaurant؛ لا يوجد احتياج مثبت لبناء
نظام منتجات أو جدول مطاعم بديل عن Merchant وCatalog الحاليين.

## 1. ما الذي تعرضه الواجهة اليوم؟

المصادر:

- [reference.json](../apps/storefront/src/features/marketplace/data/reference.json):
  12 مطعمًا، لكل منها name وcover وlogo وoffer وmeta وrating وtime.
- [merchant-detail-scenarios.json](../apps/storefront/src/features/marketplace/data/merchant-detail-scenarios.json):
  ثلاثة قوالب أصناف: برجر كلاسيك 185، تشيز برجر 215، بطاطس مقرمشة 75 جنيهًا.
- [restaurant-scenarios.ts](../apps/storefront/src/features/marketplace/data/restaurant-scenarios.ts):
  يولد 3 أصناف لكل مطعم، ويضيف 5 أمثلة لبيت البرجر؛ الناتج 41 سجل صنف محليًا،
  وليس 41 صنفًا مثبتًا في قاعدة البيانات. بيت البرجر له 8 أمثلة، والباقي 3 لكل مطعم.

أسماء المطاعم المرجعية: بيت البرجر، أصل الشاورما، بيتزا نابولي، بحريات الميناء،
كشري البلد، قهوة ومزاج، مشويات السلطان، مطبخ أم علي، سوشي هاوس، فطار زمان،
حلويات دمشق، جرين بايتس.

باقي المطاعم تستخدم أسماء وجبات عامة وصورًا معاد استخدامها. لذلك ليست هذه
القوائم منيوهات حقيقية أو بيانات جاهزة لإطلاق تجاري لمجرد ظهورها في الواجهة.

السيناريو الحالي يثبت التوصيل عند 25 جنيهًا والحد الأدنى عند 100 جنيه، ويجعل
آخر مطعم مغلقًا، وبطاطس بيت البرجر غير متاحة. هذه قواعد عرض محلية، لا معلومات
تشغيلية محفوظة. اختيار الطعام: عادي +0 / كبير +40؛ جبنة +20 / صوص +10.
اختيار المشروبات: عادي +0 / كبير +15؛ حليب +5 / كراميل +10.
أول اختيار مطلوب محدد تلقائيًا؛ الإضافات الاختيارية تبدأ دون تحديد.

| التقييم rating | لا يوجد مصدر تقييمات/ملخص تقييم عام | مطلوب فقط لأن كارت الهوم يعرضه. يحتاج مصدر حقيقي أو إبقاء العرض تجريبيًا؛ لا يتحول رقم الـfixture لتقييم عملاء موثق |
| شارة العرض offer | لا يوجد مقابل في ملف المطعم أو محرك خصومات storefront | محتوى عرض تسويقي يحتاج مصدرًا؛ شارة «خصم» أو «توصيل مجاني» لا تُطبق حسابيًا حاليًا، ولا يجوز افتراض أنها خصم منفذ |
| قريب منك / المنطقة | الفروع لها address داخلي، وليس نظام اكتشاف جغرافي عام | عنوان الفرع وحده لا يثبت القرب أو تغطية التوصيل؛ لا نحتاج خريطة جديدة للحفاظ على التصميم، لكن نحتاج تعريف المنطقة قبل تفعيل الادعاء فعليًا |

تحميل قالب tenant storefront؛ التصميم الموحد الحالي يمكن أن يبقى ثابتًا.

| احتياج الواجهة | الموجود | المطلوب للحفاظ على نفس العرض |
| --- | --- | --- |
| اسم الصنف | Product.name | إدخال نفس الاسم العربي؛ cartName يمكن اشتقاقه من الاسم، ولا يلزم نسخه في عمود آخر |
| الوصف | Product.description اختياري | موجود؛ تعبئة نفس الوصف. لا يلزم حقل description جديد |

| صور الكارت والصفحة | MediaAsset + ProductImage، صورة أساسية وترتيب | موجود؛ استخدام نفس الصور الحالية كأصول مسجلة وربط الصورة الأساسية، بدل صور seed المختلفة |
| أكثر من صورة | ProductImage[] | موجود؛ لا نحتاج حقولًا ثابتة photo1/photo2 |
| الأقسام | Category + ProductCategory، مع دعم أكثر من تصنيف | موجود؛ menuSection المحلي نص واحد، بينما الخادم يعيد categories؛ يلزم تحديد قسم عرض أو قاعدة عرض عند تعدد التصنيفات |

| حجم الصنف | ProductVariant باسم وسعر كامل وتوفر وترتيب وattributes | موجود؛ يمكن عرض نفس بطاقتي الحجم دون تغيير التصميم |
| الإضافات | مجموعات قابلة لإعادة الاستخدام وتعيينات لكل منتج | موجود؛ الاسم والوصف وsingle/multiple وmin/max والأسعار/defaultSelected والترتيب |
| إضافات تختلف حسب الحجم | variantOverrides على المجموعة والخيار والأسعار | موجود، والواجهة المحلية الحالية أبسط منه؛ يجب احترامه عند تغيير الحجم |
| كمية الإضافة | maxQuantity واختيار كميات في quote | موجود؛ الـcheckbox المحلي يمثل كمية واحدة. دعم >1 يحتاج قرار عرض إذا استُخدم فعليًا، وليس حقل DB جديدًا |
| أول حجم افتراضي | variants.position؛ لا يوجد defaultSelected للـvariant | لا يلزم schema جديد لتحقيق طلب المستخدم: اختر أول variant قابل للبيع حسب الترتيب وأرسل هويته صراحة |
| اختيارات افتراضية للإضافات | defaultSelected في تعيين الخيار للمنتج | موجود؛ يختلف عن قاعدة «أول حجم». لضمان أن الإضافات الاختيارية لا تُختار، تضبط البيانات وترسل المجموعة الفارغة صراحة عند الحاجة |
| متاح / غير متاح | Product.availability + archivedAt؛ وvariant availability | موجود في التخزين، لكن public listing يخفي المنتج غير المتاح ولا يعيد حالته؛ يلزم projection يعرض المتوقف مؤقتًا مع تعطيل الطلب، مع إبقاء المؤرشف مخفيًا |
| نفاد حجم | variant.stockQuantity وحالته في public mapping | موجود؛ الخادم يعلن نفاد كمية صفر لبعض المسارات ويعيد الفحص عند التسعير/الطلب. لا يساوي فتح/غلق المطعم |
| رابط مباشر للصنف | owner GET detail موجود؛ العام قائمة منتجات وquote | لا يوجد public product-detail GET مستقل في controller الحالي. يلزم قراءة عامة محددة أو resolver مناسب؛ أول صفحة من القائمة ليست بديلًا مضمونًا لكل الروابط |
| أصناف أخرى من نفس المطعم | المنتجات مرتبطة بـmerchantId | اشتقاق من قائمة المطعم أو query محدودة؛ لا يحتاج جدول recommendations |

الميديا الحالية تدعم upload وتسجيل metadata مع publicUrl. لذلك الحفاظ على نفس
صور المنتجات لا يتطلب اختراع نظام صور جديد؛ يلزم تجهيز الأصول والبيانات
الصحيحة تحت التاجر الصحيح. تحميل نسخة ثابتة من الصورة أو تسجيل رابطها اختيار
تنفيذي لاحق، وليس إجراءً تم في هذه المراجعة.

### فرق مهم في السعر والهوية

الواجهة الحالية تمثل الحجم داخل selection مثل size: [large]، وتجمع زيادة
الحجم مع السعر الأساسي. الخادم يفصل variantId عن selections الخاصة بالإضافات.

مثال يحافظ على نفس الوجبة المعروضة:

| الاختيار | الواجهة المحلية | تمثيله المقترح باستخدام الموجود بالخادم |
| --- | --- | --- |
| عادي | 185 + 0 | Variant بسعر كامل 185.00 |
| كبير | 185 + 40 | Variant بسعر كامل 225.00، وليس 40.00 |
| كبير + جبنة | 185 + 40 + 20 | Variant 225.00 + modifier 20.00 = 245.00 |

يمكن للواجهة أن تظل تعرض «+40» للعميل باعتباره فرق السعر بين الحجمين. لا ترسل
السعر المحسوب بدل معرف الـvariant. ولو مثلنا الحجم كمجموعة modifier مطلوبة
بدل Variant فهذا مدعوم أيضًا؛ نختار تمثيلًا واحدًا للصنف، ولا نسعر نفس الحجم مرتين.

الخادم يستخدم هوية تعيين المجموعة للمنتج group.id في quote، وليس بالضرورة
modifierGroupId الخاص بالمكتبة. الواجهة تحتاج المعرفات الحقيقية للمنتج والحجم
والمجموعة والخيار؛ قيم mock-burger وsize وcheese ليست معرفات backend.

كذلك الواجهة الحالية تختار مجموعات الطعام/المشروبات بحسب اسم قسم عربي.
عند الربط يجب أن تأتي مجموعات الاختيار لكل منتج من Catalog، بما فيها منتج
بلا أحجام أو بلا إضافات، بدل افتراض وجود الحجم والجبنة والصوص لكل منتج.

مصادر: [العقود](../packages/contracts/src/catalog.ts)،
[Public mapping](../apps/api/src/modules/catalog/catalog-query.service.ts)،
[Product mapper](../apps/api/src/modules/catalog/products/product.mapper.ts)،
[Pricing](../apps/api/src/modules/catalog/pricing/product-pricing.service.ts)،

## 4. الحقول التي لا نحتاج إضافتها إلى قاعدة البيانات

- displayPrice: تنسيق السعر بعملة مصرية وأرقام 0–9.
- cartImage: اختيار الصورة الأساسية/نسخة مصغرة منها.
- cartName وseller وmerchantName على كل صنف: يمكن عرضها من الاسم وسياق المطعم؛
  تكرارها في سجلات الطلب التاريخية له غرض مختلف ويقوم به Orders بالفعل.
- searchName: البحث الحالي مساعد محلي؛ البحث العام يمكن أن يعتمد على الاسم
  والوصف بآلية مناسبة دون أن يصبح هذا الحقل شرطًا في نموذج المنتج.
- origin: local-mock: علامة بيئة العرض وليست خاصية تجارية للصنف.
- menuSection كنص مكرر: Category الحالية تغطي الأساس؛ نحسم فقط القسم/الترتيب.
- أيقونات الأقسام، عرض الكارت 280px، عرض البوب أب 360px، مواضع الصورة والأزرار
  وألوان البنفسجي والذهبي: مسؤولية مكونات وتصميم الواجهة، وليست حقول API.
- كلمة «من» وفرق سعر الحجم: مشتقات عرض من الأسعار القابلة للبيع؛ يجب تعريف
  سعر الكارت عند اختلاف basePrice عن أقل/أول variant، حتى لا يظهر سعر مضلل.

## 5. الـAPIs الموجودة وحدودها

| المسار الحالي | ما يغطيه | الحد الذي يهم Marketplace |
| --- | --- | --- |
| GET /catalog/stores/:slug | اسم وهوية متجر مع شعار وإعدادات قالب وأول صفحة منيو | ليس قائمة مطاعم، ولا ملف مطعم تشغيلي كامل |
| GET /catalog/stores/:slug/categories | أقسام عامة cursor-paged | حتى 100 في الصفحة، وبترتيب القراءة الحالي |
| GET /catalog/stores/:slug/products | أصناف عامة cursor-paged | حتى 40 في الصفحة، يخفي غير المتاح، ولا يدعم q/category/sort في هذا controller |
| POST /catalog/stores/:slug/products/:id/quote | سعر موثوق للـvariant والإضافات | موجود؛ يُعاد استخدامه بدل إرسال أسعار الواجهة |
| POST /catalog/stores/:slug/orders | إنشاء طلب pickup/delivery مع snapshots | موجود؛ التوصيل والحد الأدنى وفتح المطعم ليست قواعد مطبقة فيه حاليًا |
| GET /storefront-handles/:handle | تحويل handle إلى storefrontSlug | ليس بحثًا أو ملف مطعم أو منيو |
| /admin/merchants | إدارة التجار بحماية AdminGuard | ليس endpoint عامًا يصلح لكروت Marketplace |
| /owner/catalog/products و/categories و/modifier-groups و/media | إدارة محتوى الأصناف للتاجر | موجودة؛ يحافظ الربط على tenant scope ولا يستخدمها الزائر العام |
| /auth/owner/storefront | القالب واللون والشعار | لا يغطي وصف المطعم/غلافه/نوع أكله/ساعات العمل/رسومه |

لا يوجد حاليًا public Marketplace discovery في هذه الـcontrollers. يلزم
قراءة محدودة للمطاعم المنشورة ببحث وفلاتر وصفحات؛ لا نسحب قائمة الإدارة ولا
ننفذ طلب كتالوج مستقل لكل تاجر لمحاكاة البحث العام. أي توسعة للقراءة العامة
تحافظ على tenant storefront وPOS الحاليين وتضيف احتياج Marketplace بوضوح.

## 6. أثر الاختلاف على السلة والطلب

- السلة المحلية تميز productId مع selection. الربط يحتاج أيضًا variantId
  وهوية تاجر مستقرة؛ تظل نفس شاشة السلة، لكن هوية السطر تشمل كامل الاختيار.
- إنشاء الطلب الحالي يحسب الإجمالي من مجموع سطور المنتجات؛ رسوم التوصيل 25
  الحالية ليست جزءًا من حسابه أو receipt breakdown. يلزم احتسابها وحفظها في
  الطلب وإرجاع تفصيل ثابت، لا زيادتها في المتصفح فقط.
- فحص غلق المطعم والحد الأدنى والتغطية يجب أن يحصل في الخادم وقت الطلب، وليس
  مجرد تعطيل زر بالواجهة.
- public create لا يحتوي requestId/idempotency key؛ منع الضغط مرتين محليًا
  لا يمنع التكرار بعد timeout/retry. معالجة ذلك مطلوبة لمرحلة الطلب الحقيقية.
- الخادم يملك pending/accepted/rejected/preparing/ready/completed/cancelled؛
  الواجهة المحلية تملك demo statuses بينها in-transit. لا يوجد public read
  للتتبع/السجل في controller العام الحالي. وجود مسارات POS للتوصيل لا يجعلها
  public customer tracking؛ تحتاج قراءة محمية بالهوية أو وصول الطلب المناسب.
- مدفوعات POS الحالية ليست إثبات وجود دفع أونلاين للـMarketplace. لا يحتاج
  كارت الوجبة أو المنيو تغييرًا بسبب تأجيل هذه المرحلة.
- بعض قواعد المخزون/الاشتراك قد ترفض طلبًا حتى إن ظهر المنيو؛ حالة إتاحة
  Marketplace يجب أن تُعرّف بوضوح بدل مساواة وجود Merchant بإمكانية الشراء.

## 7. المحتوى الحالي والـseed: ليسا نفس البيانات

[catalog-seed-data.ts](../apps/api/src/scripts/catalog-seed-data.ts) يحتوي أمثلة
مختلفة: Classic Beef Burger بسعر 165.00 وأقسامًا مثل Meals وBurgers، مع
Regular bun وBrioche bun ومجموعات اختيارات أوسع. بينما الواجهة الحالية تعرض
برجر كلاسيك 185 وأقسامًا عربية واختيارات مختلفة.

[seed-catalog.ts](../apps/api/src/scripts/seed-catalog.ts) ينتج صور PNG محلية
مرسومة من ألوان، وليس نفس صور الوجبات الحالية. كما يستهدف Merchant موجودًا،
ولا يثبت وجود المطاعم المرجعية الاثني عشر في قاعدة البيانات.

بالتالي: تشغيل هذا الـseed كما هو لا يحقق «نفس الاسم والوصف والصورة والسعر».
نحتاج حزمة محتوى مطابقة للواجهة، مع جدول ربط fixture → merchant/product/
variant/category/media IDs. تُجهز كبيانات تطوير/عرض معلنة، ولا تستبدل محتوى
مطاعم فعلية أو تُنشئ حسابات مالكين/بيانات اتصال افتراضية دون نطاق تنفيذ محدد.
المراجعة لم تنفذ أي استيراد، ولا تؤكد ما إذا كان seed معين قد شُغّل سابقًا.

## 8. ما الذي نضيفه وما الذي نعيد استخدامه؟

### إضافات ضرورية للحفاظ على التجربة الحالية عند الربط

1. محتوى مطعم عام قابل للإدارة: وصف/نوع أكل، وغلاف كارت، وطريقة شعار مناسبة
   للصور الحالية. حقول الاسم والهوية الحالية يعاد استخدامها.
2. إعدادات تشغيل معلنة: استقبال الطلبات، التوصيل/الاستلام، الرسوم والحد الأدنى
   ووقت التوصيل. ساعات العمل التفصيلية عند اعتماد الفتح التلقائي.
3. قراءة عامة لاكتشاف المطاعم وملف المطعم، مع قواعد نشر وحدود وتصفية واضحة.
4. قراءة أصناف مناسبة للعرض تشمل غير المتاح مؤقتًا، وقراءة صنف مباشر، وقرار
   ترتيب الأقسام/الأصناف وتصنيف المنتج متعدد الأقسام.
5. مصدر للتقييم/شارة العرض إذا احتفظنا بكل محتوى كارت الهوم؛ لا نحتاج نظام
   تقييمات كاملًا أو خصومات كاملًا فقط من أجل تعبئة نص تجريبي، لكن لا ننسبه
   لعملاء حقيقيين أو نعد بخصم قبل تطبيقه.
6. تحديث إدارة المطعم لتعبئة الحقول الجديدة. Product Builder الحالي يدير
   الأساس: أسماء/أوصاف/صور/تصنيفات/variants/modifiers؛ لا نعيد بناءه.
7. حزمة بيانات مطابقة للـUI، وطبقة تحويل بيانات في الواجهة، ثم تسعير وطلب
   خادميان بعد اتفاق قواعد التشغيل، دون إعادة تصميم.

### لا يحتاج بناء جديد

نموذج Product وCategory، صور المنتجات، variant prices، modifier assignments،
defaultSelected للإضافات، اختيار أول variant في العرض، quote الأساسي،
snapshots الطلب، ومكونات المنيو/البوب أب/صفحة الوجبة نفسها.

### توزيع المسؤوليات المقترح، لا عقود إنتاج معتمدة

- Merchants: هوية التاجر ونشاطه وملفه ضمن ملكيته الحالية.
- Storefront: محتوى العرض وإعداداته وتركيب القراءة العامة واكتشاف Marketplace.
- Catalog: المنتجات والتصنيفات والاختيارات والصور المرتبطة والتسعير والتوفر.
- Orders: تطبيق قواعد الطلب والإجماليات وحفظ الرسوم والاختيارات والحالات.
- Media: تسجيل/رفع الأصول؛ وAuth/Payments عند تناول هوية العميل والدفع.

المكان النهائي لإعدادات ساعات العمل/التوصيل المشتركة يحتاج تصميمًا صريحًا
قبل التنفيذ، خاصة إن أصبح الإعداد على مستوى الفرع. لا نقرر جدولًا جديدًا أو
DTO نهائيًا بمجرد أسماء حقول احتاجتها الواجهة.

## 9. ترتيب العمل المقترح بعد هذه المراجعة

1. تثبيت هذه المطابقة كمتطلبات بيانات، مع الحفاظ على تصميم Marketplace الحالي.
2. حسم البيانات التشغيلية التي ستدار لكل مطعم، وظهور التاجر للعموم؛ وتجهيز
   الحقول/الإدارة والقراءة الناقصة أولًا.
3. تجهيز محتوى مطابق للمراجع وصور صحيحة ومعرفات مستقرة، دون تشغيل الـseed القديم
   باعتباره نسخة من الواجهة الحالية.
4. تحويل مصدر القراءة للمطاعم والمنيو وصفحة الوجبة فقط، باستخدام نفس المكونات.
5. توصيل variants/modifiers الحقيقية والـquote، ثم إنشاء الطلب ورسومه.
6. معالجة سجل العميل والتتبع والدفع كاحتياجات مستقلة مثبتة، لا افتراض أنها جاهزة
   لأن نظيرًا محليًا أو endpoint محميًا للـPOS موجود.

بدء أي تعديل API/DB/عقود أو ربط فعلي يظل خطوة منفصلة عن هذه المراجعة.
